## 6. 工作流与验收规矩（用户反复强调，务必遵守）

1. **先方案、后实现**：视觉/交互先给 2~3 个方案（真实渲染或清晰描述），用户选完再动代码；
2. **验收只认真实渲染图 / 用户真机截图**；测试全绿 ≠ 效果对；
3. **测试只做定向**：改完跑相关测试 + analyze；全量测试只在发版前跑一次；
4. **一个安装包只装一个已确认主题**；不要边猜边发；
5. 不擅自改数据库结构、不改核心功能逻辑、不加听力；改动范围尽量小；
6. 遇到 GitHub 网络失败：重试 push（`git -c http.version=HTTP/1.1 push origin master`），
   网络差时 gh release 也要重试；发布后核对 digest；
7. 用户会以真机截图指出问题，**先复现/定位根因，再修**，不在表面加样式。

### Agent Teams 使用经验（本次已验证）

- 把独立部分拆给 3 个 fresh teammate 并行：持久化 store、发现引擎、频道页 UI；
  Lead 负责契约（API 签名/写作用域/验收口径）与集成；
- 写作用域必须分开，否则会互相覆盖；任务板用 `team_task_create` 记录契约与 write scope；
- 再加 1 个**只读质检 teammate**（不改文件，只跑 analyze/test + 需求逐条对照），

- 并行 teammate 偏慢（读代码+写大文件），但质量比单线程边写边猜更稳。

## 7. 发版流程（照抄即可）

```powershell
# 1) 版本号（pubspec.yaml）：version: X.Y.Z+BUILD
# 2) 写 docs/release-notes-vX.Y.Z.md
# 3) 构建（arm64，release）
$env:FLUTTER_ALREADY_LOCKED='true'; flutter build apk --release --target-platform android-arm64 --no-pub
# 4) 校验包内版本
aapt dump badging build\app\outputs\flutter-apk\app-release.apk | findstr version
# 5) 归档符号 + 桌面副本
Copy-Item build\app\outputs\mapping\release\mapping.txt tool\symbols\X.Y.Z\mapping.txt
Get-FileHash build\app\outputs\flutter-apk\app-release.apk -Algorithm SHA256
# 6) 提交 + tag + push（网络失败重试）
git add -A; git commit -m "chore: vX.Y.Z 构建符号归档"; git tag -f vX.Y.Z
git -c http.version=HTTP/1.1 push origin master; git -c http.version=HTTP/1.1 push -f origin vX.Y.Z
# 7) 发布（notes 用文件；上传慢，放后台跑）
gh release create vX.Y.Z build\app\outputs\flutter-apk\app-release.apk `
  --title "ReadFlow vX.Y.Z · 一句话主题" --notes-file docs/release-notes-vX.Y.Z.md
# 8) 核对 digest 与本地 sha256 一致
gh release view vX.Y.Z --json assets
```

- 本机 build 约 3~5 分钟；**gh release 上传可能 10~25 分钟**（前台会超时，放背景任务轮询）；
- APK 只发 arm64；asset 名固定 `app-release.apk`（App 内更新靠它）。
