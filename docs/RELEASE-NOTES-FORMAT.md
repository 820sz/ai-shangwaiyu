# 发布说明书写规范（v3，2026-11-01 用户要求）

> 用户原话：
> 「更新内容播报是属于'给我汇报工作的提示词'，而不是规规矩矩的升级的地方
> '1，xxx。2，xxx'。」
>
> 所以从 v2.14.0 起，**GitHub Release 的正文必须按本文件写**，
> App 内更新弹窗只解析「## 更新内容」小节，别的写作习惯会直接显示成兜底长文。

---

## 一、格式

````markdown
# ReadFlow v2.14.0 · 一句话主题

> 可选：一行背景，不显示在弹窗里。

## 更新内容

1. 识图追问抽屉现在会记住你上次看到的位置。
2. 移动词汇到已有分类时不再重复新建分类。
3. 底栏「材料 / 练习」改名为「输入 / 输出」。
4. 识别结果里的词汇卡片现在显示音标。

## 技术细节

- 可选：dbVersion 18→19、迁移说明、测试数量、构建信息等。
- 这一节**不会**出现在 App 的更新弹窗里，只给维护者/仓库访客看。
````

### 硬规则

1. **必须有「## 更新内容」小节**（`更新内容` / `更新说明` / `本次更新` 都认）。
2. 每条一行，用 `1. ` / `2. ` 编号；**一条一句话**，不写"我做了什么"式汇报语。
3. 用**用户能懂的语言**：写"识图追问抽屉会记住位置"，不写"重构 follow_up_drawer 的
   scroll controller 生命周期"。
4. 每条不要以句号结尾（弹窗会自动去掉），但可以带括号补充。
5. 最多 8 条（弹窗默认展示 6 条，可展开）；超过的部分用户看不到，重要内容放前 8 条。
6. `## 技术细节` / `## 验证` / `## 风险` 等小节**不会进弹窗**，可以随便写技术话。
7. 不要在这一节里写内部文件名、commit、AI 提示词之类的工程细节。

## 二、解析规则（App 侧实现）

`UpdateService.parseReleaseNotesForDisplay(body, {maxItems = 8})`（`lib/services/update_service.dart`）：

- 优先取「更新内容 / 更新说明 / 本次更新」小节，到下一个 `#` 标题为止；
- 没有该小节时：收集**顶层**列表项（`- ` / `1. ` / `1、`），遇到
  「验证 / 测试 / 还没做 / 风险 / 附录 / 后记 / 技术细节」标题后停止收集；
- 清理 markdown：`**`、`__`、反引号、`[文字](链接)` → `文字`、`<html>` 标签；
- 缩进子项、表格、引用块、纯链接行不单独成条；
- 去重；最多 8 条；解析不出任何条目时兜底取正文第一段前两句。
- 单测：`test/update_service_test.dart` 的 `parseReleaseNotesForDisplay` 组。

## 三、自动检查更新（App 侧行为）

- 进 App 后：首帧 + 开屏结束后自动检查一次（最多等 10 秒让 Navigator 就绪）；
- **每天最多自动检查一次**（Hive `update_last_auto_check_at`），手动「检查更新」不受限；
- 网络失败静默（只 `debugPrint` 留痕），不弹错误打扰用户；
- 有新版本才弹窗；弹窗内容 = 上面解析出的编号清单。

## 四、发版流程里要做的

1. 新建 `docs/release-notes-vX.Y.Z.md`，按本规范写；
2. `gh release create vX.Y.Z <apk> --title "..." --notes-file docs\release-notes-vX.Y.Z.md`；
3. 发版后核对 digest 与远端同步（见 `docs/HANDOFF-NEXT-SESSION.md` §3）。
